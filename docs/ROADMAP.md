# Operational roadmap (Paseo heartbeat queue)

This file is the working queue for the automated build loop, which runs as two Paseo heartbeats on agent `7df45c0` (claude-haiku-5-5, per `paseo agent inspect`): a **builder** heartbeat (`0b1cde69`, cron `0 * * * *`, Europe/Madrid) picks the top "Ready to build" item and ships, commits (never pushes), screenshots and shares a Cloudflare tunnel every hour; a **supervisor** heartbeat (`bc87feb0`, cron `30 */6 * * *`) reviews the unpushed work, verifies the tests, unblocks anything blocked by making a recorded decision, pushes, publishes the Pages link and changelog, researches other embroidery software (Wilcom, Ink/Stitch and friends) and refreshes this queue. Each firing is stateless and re-reads this file from scratch; that's by design. The earlier arrangement (a `paseo schedule` starting a fresh Haiku agent each hour, id `44e95934`) is gone — self-registered heartbeats work now. Strategic scope and decisions still live in `docs/PLAN.md`; detailed build history lives in `docs/IMPLEMENTATION_STATUS.md`. This file only tracks what to build next and what just shipped.

Rules for the builder: always take the top item in "Ready to build" you haven't finished. If it's ambiguous or too big for one hour, scope a complete, tested slice of it yourself — do not wait for a decision. **Keep looping within the hour**: after shipping one item, check your elapsed time, and if you're comfortably under budget (rule of thumb: well under 40-45 minutes used), go pick up the next item instead of stopping. The first three hourly runs each finished in 4-11 minutes and still stopped at one item — that is under-using the budget, not a success condition. Never leave a heartbeat with nothing shipped. If the queue is empty, pull the next concrete item from `docs/PLAN.md`'s open work yourself, add it here, and build it.

Rules for the supervisor: verify tests actually pass and diffs match commit messages before moving an item to "Done this cycle". Keep at least 4 concrete, unambiguous items queued at all times. Push to `origin/main` only once verified.

## Ready to build

Queue refilled by the 2026-10-24 supervisor run from the research in the Decisions section. Items 5 to 7 come from competitor features; 1 to 4 came from the earlier builder queue.

1. **Heart bling stone** — Add `heart` to `blingShape` (a parametric heart outline scaled to the stone size, its point along the path, fixing ring at two-thirds size), the same way the star and hexagon were added: engine validation and shape, Spanish label (Corazón, check `src/i18n.js` first), the Stone shape option, the MCP enum and help text, the e2e shape test, a feature case in `scripts/feature-shots.mjs`, and a screenshot.
2. **Bling: one or two fixing rings** — Bling stones always sew two concentric fixing rings. Add `blingRings` (1 or 2, default 2) with a Fixing rings select in the bling settings and an MCP key. Engine test that one ring sews fewer stitches than two on the same path and the stone's size is unchanged, e2e shape test extended, a feature case, screenshot.
3. **Bead shape: dash or dot** — Beads are one dash across the path at each point, and the editor has no other bead shape (`docs/PLAN.md` limit). Add `beadShape` (`dash`, the default, or `dot`): a dot sews one stitch at each point, for beads sewn on as single dots. Engine test (a dot path sews fewer stitches than a dash path on the same line, both within the path's bounds), a Bead shape select shown for beads, the MCP key, e2e test, screenshot.
4. **Twin beads** — Source: GMI Stilista's brochure lists single and twin beading devices (checked 2026-10-24). Welcome has twin sequins but only single beads. Add a `beadTwin` option that sews two beads side by side across the path, each a bead's length apart from the centre line, the same way `sequinTwin` works. Engine test (twin beads sew about twice the stitches, and sit either side of a horizontal path), a checkbox shown for beads, the MCP key, e2e test, screenshot.
5. **Pull compensation per side for satin** — Source: Wilcom EmbroideryStudio 2026 release notes list independent pull compensation for each side of an object (checked 2026-10-24). Welcome has one `compensation` value (0–2 mm). For satin columns, add `pullLeft` and `pullRight` (0–2 mm, each overriding `compensation` for that side). Engine test (a column with a larger right pull is wider on the right than on the left), the two numeric fields shown for satin, the MCP keys, e2e test, screenshot.
6. **Laydown underlay for textured fabric** — Source: Hatch Embroidery 3's Laydown Stitch, which lays a light fill under the design so that the nap of terry towelling and fur stays flat (checked 2026-10-24). Add an underlay type `laydown`: a single fill at a wide row spacing (about 4 mm) under a fill or satin, sewn before the top stitching. Engine test (a laydown underlay adds stitches under the fill, and an unknown underlay type is still rejected), a Spanish label in the underlay select, the MCP enum, e2e test, screenshot.

## Decisions

- **2026-10-24 — Safari device check (blocker, left open).** `docs/PLAN.md` lists a real Safari device check as needing a device. This environment has none, so it cannot be done here. Decision: keep the item open as a known limitation rather than mark it done. The WebKit benchmark (`scripts/bench-browser.mjs`, Playwright-core 1.58.2) is the substitute the builder can run, and it stays documented as not a Safari check. Jose can close it on a device.
- **2026-10-24 — Desktop builds not run yet (blocker, unblocked).** `desktop.yml` builds Linux, macOS and Windows but only runs on a `v*` tag or a manual `workflow_dispatch`, so it had never run. Decision: dispatch it manually on `main` after the push. Reason: the repository is public, so GitHub-hosted runners cost nothing, and a manual run creates no tag and no release. Result: the first run (40034349184, on `1e4df8a`) failed on windows-latest with `spawnSync npm ENOENT` in `scripts/prepare-desktop.mjs`, because npm is `npm.cmd` on Windows. Fixed in `036109f`, which spawns `npm.cmd` through a shell on win32. The second run (40035382088, on `036109f`) succeeded on ubuntu-22.04, macos-14 and windows-latest. The `desktop/electron/` packager is gitignored and not part of the repo, so its equivalent call was fixed only in the local copy and is not shipped.
- **2026-10-24 — Stale bead documentation (fixed).** `docs/IMPLEMENTATION_STATUS.md` still described beads as three passes after `076febe` made them one. Decision: correct the line and point it at the bead entry. Docs-only change, so no test rerun was needed.
- **2026-10-24 — Roadmap header agent model (fixed).** The header called agent `7df45c0` Claude Opus 5, but `paseo agent inspect` reports `claude-haiku-5-5`. Decision: correct it to the reported model.
- **2026-10-24 — Other project's agent (not touched).** Agent `16cf467` is a heartbeat in `~/Code/pigma`, another project. It is running and not waiting on a permission. Decision: leave it alone, since it is outside this repo.
- **2026-10-24 — Bling stone library and true 3D warp (not blockers).** `docs/PLAN.md` lists both as not started. Decision: they stay in PLAN as future work. The queued items (stones turn with the path, heart, fixing rings, bead shape) are the small slices of them that fit one hour.
- **2026-10-24 — Old schedule history in `docs/ORCHESTRATION.md` (kept).** That file describes the retired `44e95934` schedule. Decision: leave it as the record of how the loop was first set up, since it is history rather than a live instruction.

- **2026-10-24 — Trim records in SEW (no build).** The queued item asked us to match trim encoding against pyembroidery 1.5.1's SEW writer. Checked: pyembroidery 1.5.1 has a SEW reader (`SewReader.py`, which reads stitches, jumps `80 02`/`80 04`, stitches `80 10`, colour changes `80 01`, and ends at any other control) but no SEW writer. None of the 15 pinned SEW samples contains a trim command, so there is no reference to copy a trim code from. Inventing one would produce files nobody can check. Decision: do not add a trim code. SEW export keeps writing trim travel as jumps, and `readSew` reads them back as jumps (only the JEF reader infers trims from long travel). Revisit only if a SEW file with a real trim record (from a Janome or Wilcom export, or a reference writer) is added to `fixtures/`; then pin it the way the other SEW samples are pinned.
- **2026-10-24 — Competitor research and queue (decision).** Searched Ink/Stitch, Wilcom EmbroideryStudio 2026, Hatch 3, Embrilliance, Bernina ARTlink, PE-Design and sequin/bead sources. Items 5 to 7 in the queue were taken from that research, each one small enough for an hour. Left out for now because they are too big for one hour: a multi-position hoop and file-splitting feature (Hatch 3), a keyboard lettering collection (Hatch 3), and a multi-machine queue (PE-Design Next's Link function). They belong in `docs/PLAN.md` as future work. Not verified: the Ink/Stitch 3.3.0 notes (stroke paths as satin columns, several short-stitch inset values) are already close to what Welcome does, so they were not queued. Hatch 4 and PE-Design 12 could not be verified from search results and were not used.
- **2026-10-24 — Windows npm spawn (fixed).** Covered by the desktop entry above. The fix is in `scripts/prepare-desktop.mjs` only, because `desktop/electron/` is gitignored.
